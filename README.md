# 离线语音唤醒 + 固定口令识别（方案第 5 点）

乒乓球智能裁判终端里的"语音纠错"子系统：**完全离线**，先说唤醒词（默认「小裁判」），
再说固定口令（左方加一分 / 撤销 / 重置比分 / 确认这一分 ……），口令只改比分状态，
不动原始视频和事件日志。

自适应计分界面另有独立仓库：
[xwrjym/pingpong-scoreboard-ui](https://github.com/xwrjym/pingpong-scoreboard-ui)。

设计原则（对应方案 2.3 第 5 条）：

* 只用**固定短语集合**识别，不做开放式语音理解，避免误操作；
* 判据不满足时**拒绝执行并提示重说**，绝不猜一个意图去改比分；
* 危险动作用**二次确认**（重置比分要说两遍）；
* 每个动作写 JSONL 日志（含原始识别文本、相似度、改前改后比分），便于复盘误识别。

## 3. 数据流

```
麦克风/文件 ──► 16k 单声道 PCM 帧(100ms)
                  │
                  ├─ 能量 VAD：切句（静音 400ms 收尾 / 单段最长 3s）
                  │
     待唤醒 idle ──┤  唤醒模式：子序列 DTW 只在唤醒词模板上匹配
                  │        └─ 命中 ──► 播"在"，进入聆听窗口
                  ▼
     聆听 listening  口令模式：整段子序列 DTW 在口令模板上匹配
                     ├─ 距离进阈值 且 与其它意图差距够大 ──► 候选文本
                     └─ 否则 ──► 提示"请再说一遍"（超次退出）
                  │
                  ▼
            拼音近音纠错层（matcher/parser）：同音错字、口语填充词、唤醒词前缀
                  │  绝对阈值 + 歧义间隔
                  ▼
            比分状态机（score.py）：加/撤销/重置二次确认/落盘 + JSONL 日志
                  │
                  ▼
            反馈：蜂鸣 + 中文播报（可替换成开发板上的音频播放）
```

唤醒和口令**连着说**（"小裁判左方加一分"）也能识别：引擎命中唤醒词后，
会在同一段语音里再匹配一次口令；Vosk 后端则靠 1.5s 音频回灌实现同样的效果。

## 4. 两个后端：为什么默认 DTW，什么时候换 Vosk

| | DTW 模板匹配（备用） | Vosk（Kaldi 小模型，默认） |
|---|---|---|
| 依赖 | 只要 numpy | 需下载 42MB 中文模型 |
| 注册 | 需本人录音（3 遍/短语） | 开箱即用，无需注册 |
| 说话人 | 说话人相关，换人要重注册 | 说话人无关 |
| 自由说话 | 只认注册过的短语 | 能接续说、可做全句识别 |
| 资源 | 每段语音几十毫秒 CPU，内存 <5MB | 常驻解码，PC 上约占几个百分点 CPU，模型常驻 100–200MB |
| 适用 | 说话人固定、要极省资源（低成本板卡） | **业余自用、双方轮流打、说话人经常换（本项目采用）** |

切到 Vosk（一行配置）：

```powershell
# 模型下载（alphacephei 在国内很慢，慢的话用 --url 换成自己的镜像）
.venv\Scripts\python.exe tools\download_model.py
.venv\Scripts\python.exe -m tt_voice.cli --engine vosk mic
```

`config.json` 里 `engine` 选 `"vosk"` 或 `"dtw"`（**默认已按现场情况设为 vosk**：
无裁判、双方轮流对打，说话人经常换，模板法需要每人重新注册，不划算）。
Vosk 后端用**受限词表（grammar）**解码：唤醒只认唤醒词、口令只认口令表，
这样既省 CPU 又能压误唤醒；如果模型词典缺字会自动降级为全词表并在日志里提示。

### 4.1 这套实现里三个和 Vosk 有关的坑（都已经修掉，代码里有注释）

1. **grammar 里不能写阿拉伯数字**：中文小模型的词典没有 "1"，把「左方加一分」拆成
   `左 方 加 1 分` 会被静默丢掉，识别结果变成"左方加记分"，而且置信度还有 0.97，非常隐蔽。
   现在 grammar 用保留中文数字的归一化（`normalize_light`）。
2. **唤醒词要不等静音就触发**：Vosk 默认等一句话说完才出结果，用户"小裁判撤销"一口气说完时，
   唤醒识别器会把「撤销」也吞进自己的结果（实测得到"小裁判小"）。
   现在唤醒模式监听**部分结果**（`PartialResult`），唤醒词一冒头就唤醒。
3. **唤醒后的回灌音频里会混进唤醒词残字**：受限词表会把"小裁判"硬塞成最近的口令字符
   （实测"开开右方加一分"）。现在唤醒后 `wake_tolerant_s`（默认 3s）内，口令匹配按
   "口令可以出现在句子任意位置"来对齐，之后恢复正常严格匹配。

## 5. 与计分状态机（第 4 点）的接口

`tt_voice.score.ScoreBoard` 现在就是 `tt_referee.voice_compat.SharedScoreBoard`
（由 `tools/sync_referee.py` 从裁判工程同步）。视觉事件、语音纠错、实体按键
改的是同一份比分、同一条历史与同一条审计日志；执行 `python tools/sync_referee.py`
可以在两个工程之间保持规则一致。

语音只通过 `ScoreBoard` 改状态，视觉侧只管"提出疑似得分"：

```python
from tt_voice.config import load_config
from tt_voice.score import ScoreBoard

board = ScoreBoard(load_config())

# 视觉状态机：疑似得分 -> 等语音确认
board.propose_point("left", confidence=0.87)
# 语音说"确认这一分" -> 提交；说"撤销" -> 回退

# 需要显示层的接口
board.snapshot()      # {"left":3,"right":2,"pending":...,"awaiting_reset_confirm":False,"can_undo":True}
board.score_text()    # "左方3比2右方"
board.save() / board.load()   # 断电恢复
```

意图只有这 7 个（口令说法在 `config.json` 里增删，代码不用改）：
`score_left`、`score_right`、`undo`、`reset`、`confirm`、`report`、`dismiss`。

## 6. 算法细节与调参

### 6.1 前端

MFCC(13) + 一阶差分 = 26 维，帧长 25ms / 帧移 10ms，26 个 mel 滤波器；
**先按能量剪掉首尾静音，再只在有声帧上做倒谱均值归一化（CMN）**；距离用余弦距离。

这条顺序是踩坑换来的：如果先 CMN 再剪静音，前后静音长度不同会把倒谱均值拖偏，
同一句话"整段匹配距离 0.79、分段匹配距离 3.76"，识别直接崩。

前端选择有实验支撑（`tools/compare_frontends.py`，12 个短语、clean vs SNR10dB）：

| 前端 | 距离度量 | 类内(带噪)最大 | 跨意图最小 | 比值 |
|---|---|---:|---:|---:|
| CMN | 欧氏 | 1.922 | 1.135 | 0.59 ❌ |
| CMN | 余弦 | 0.056 | 0.071 | 1.26 ✅ |
| CMN+CMVN | 欧氏 | 0.131 | 0.115 | 0.88 ❌ |
| 谱减+CMN | 余弦 | 0.056 | 0.071 | 1.26（与 CMN 完全相同）|

两个结论：

* **余弦距离**在 MFCC 上明显优于欧氏（比值 0.59 → 1.26）；
* **谱减对稳态噪声没有增量**：稳态噪声的谱减等价于 log-mel 域的常量偏置，
  正好被 CMN 完全吸收（两者数值一模一样就是证据）。谱减只在非稳态噪声下才值得加。

### 6.2 判据：绝对阈值 + 跨意图幅度余量

* 绝对阈值：注册时同一短语录 N 遍，两两算 DTW 距离，取类内最大距离 × 1.3 自标定，
  存在模板库里（不用手调）；
* 幅度余量：命中的候选还必须和**其它意图**的最优距离拉开 `dtw_margin`（默认 1.2）倍，
  否则判为歧义 -> "请再说一遍"。这条专门用来挡"某个短语阈值本来就松、于是什么都匹配到它"
  的情况；只比较不同意图，所以"左方加一分 / 左方加分"这种同意图的相近说法不会互相顶掉。

### 6.3 抗噪与鲁棒性

注册时会自动生成**加噪副本**（默认 SNR 15/10 dB）作为额外模板，
匹配时取"最像的那条模板"，等价于把噪声工况也注册进来。
注意造测试集和注册必须用**不同的噪声种子**，否则属于泄题（这个坑也踩过）。

另外一个容易被忽略的语义坑：**"模板出现在句子任意位置"必须要求模板整条对齐上**，
只是允许它的起止位置自由。早期实现写成了"取动态规划最后一行的最小值"，
等于允许只匹配模板的一小段，结果「帮我把灯关掉」因为首字"帮/报"声母相同，
被判成"报分"（分数 0.81）。声学层的子序列 DTW 和文本层的拼音对齐都有这个问题，已一并修正。

### 6.4 常用调参项（config.json）

| 字段 | 默认 | 作用 |
|---|---|---|
| `wake_words` | `["小裁判"]` | 唤醒词，可多个 |
| `engine` | `"dtw"` | `dtw` / `vosk` |
| `listen_timeout_s` | 6 | 唤醒后等待口令的窗口 |
| `max_commands_per_wake` | 3 | 一次唤醒内最多执行几条口令 |
| `max_reask` | 1 | 允许"请再说一遍"几次 |
| `reset_confirm_timeout_s` | 8 | 重置二次确认的有效期 |
| `dtw_margin` | 1.2 | 跨意图距离倍数（调大更保守） |
| `dtw_end_silence_ms` | 400 | 断句静音长度；说话停顿长的人要调大 |
| `dtw_max_segment_ms` | 3000 | 单段最长，超过就强制断句 |
| `vad_margin_db` | 8 | VAD 门限（现场噪声大就调大） |
| `match_threshold` / `match_margin` | 0.80 / 0.04 | 文本纠错层的相似度阈值（Vosk 链路常调） |

## 7. 验收结果

### 7.1 真人验收（v0.3，2026-10-21，73 条，手机经 UU 远控作麦克风）

| 指标 | 本轮 v0.3 | 上一轮 v0.2（蓝牙耳麦） | 随包合成集 |
|---|---:|---:|---:|
| 唤醒率 | **15/15 = 100%**（含 5 条 1.5–2 米远场） | 2/3 = 66.7% | 15/15 = 100% |
| 误唤醒率 | **0/6 = 0%** | 0/6 = 0% | 0/12 = 0% |
| 口令准确率 | **49/49 = 100%**（误判 0，漏识别 0） | 44/49 = 89.8% | 64/64 = 100% |
| 连说成功率 | **3/3 = 100%** | 3/3 = 100% | 6/6 = 100% |

本轮 49 条口令的解码文本**全部一字不差**（上一轮有 12 条掉首字、靠字数冗余救回），
说明采集端修复生效；3 条连说全部执行成功，6 条干扰无误唤醒、无误执行。
逐条明细见 `realdata4/eval_report_vosk_vosk.csv`（首次录制 2 条空录音，已用
`tools/rerecord.py` 定点补录）。

上一轮（v0.2，蓝牙耳麦）的归因如下，本轮已按此修复并验证：

* **失败全部是"拒识"，没有一条被错判成别的口令**——宁可让用户重说，这是设计取向。
* 失败集中在**短口令**：按字数看，2 字口令 3/8，4 字及以上 39/39 全对。
* 根因是**采集端把起音削掉了**：用真人录音做"削掉起音 N 毫秒"的对照实验，
  2 字口令削 160ms 就全灭，4~5 字口令削 80ms 还能保 80%、削 240ms 仍有约一半活着。
  所以短口令天生脆，长口令有冗余能扛。
* 蓝牙耳机（HFP 通话麦）的噪声门 + 每次开流的链路切换时间是主要嫌疑，
  已经据此改了录音工具（见 7.3）和推荐的说话方式。

由此得到三条现场建议：

1. **优先用长说法**：`撤销上一分` / `现在比分` / `确认这一分` / `重新计分` / `先不打了`。
   短说法（`撤销`/`报分`/`没错`/`重来`/`退出`/`暂停`）仍然支持，但只建议在安静、近场、麦克风链路好的时候用。
   （实验证明：把短说法从口令表里删掉反而更差 41/49，因为用户还是会说短句、grammar 会把它掰成别的意图。）
2. **麦克风别用蓝牙通话麦**：换成有线/USB/阵列麦，或让耳机工作在音乐模式（A2DP，若系统允许其麦克风）。
3. 说话前留半拍：先让提示音响过再开口（工具里已经加了提示音，见 7.3）。

### 7.2 另一台电脑上的 AI 发现并修掉的实时链路缺陷（已合并回主工程）

现象：唤醒成功后系统平白播报"请再说一遍"，而这次播报又让麦克风静音了一秒多，
把用户紧接着说的口令整句丢掉（日志表现为"没听到"）。

根因：唤醒词的音频被回灌进口令识别器后，被解码成"假口令"（`销才分` 之类，
相似度 0.27~0.55）；该结果定稿得晚，被错误标记成 `live`（真实输入）而不是
`preroll`（回灌回声），于是触发了本不该有的重说提示。

修复（**感谢另一台电脑上的那次验收排查**）：

| 文件 | 改动 |
|---|---|
| `tt_voice/engines/vosk_engine.py` | 回灌结束时记录块位置；此后定稿的结果只要**第一个字的起点**落在回灌区间内，就标记为 `preroll` |
| `tt_voice/engines/base.py` | 接口补 `mark_handoff()` 空实现（DTW 后端不受影响） |
| `tt_voice/app.py` | 回灌结束后调用标记；并把半双工静音收窄到"比分播报"这类含口令词的播报，`在/请再说一遍/没听到` 不再占用麦克风 |

### 7.4 合成集（随包自带，可一键重跑）

跑法：`python -m tt_voice.cli eval testdata`（97 个样本，逐条明细见
`testdata/eval_report_dtw_templates.csv`）。

测试集由 `tools/make_test_wav.py` 用 Windows 中文 TTS 生成，覆盖：
唤醒词 3 种语速 × 5 种信道（干净/SNR20/SNR10/混响/远场）、
32 条口令（含同义说法）× 2 种信道、3 条"唤醒+口令连着说"、12 条干扰句
（含"左边加一份""右方落后一分"这类近似干扰）。

| 指标 | Vosk（默认，49 条口令说法） | DTW（本人模板，同样 97 样本） |
|---|---:|---:|
| 唤醒率（15 个唤醒样本） | 15/15 = 100% | 15/15 = 100% |
| 误唤醒率（12 个干扰样本） | 0/12 = 0% | 0/12 = 0% |
| 口令准确率（64 个口令样本） | 64/64 = 100% | 64/64 = 100% |
| 连说（唤醒+口令一口气说完） | 6/6 = 100% | 6/6 = 100% |

逐条明细：`testdata/eval_report_vosk_vosk.csv`（Vosk）、
`testdata/eval_report_dtw_templates.csv`（DTW）；完整日志 `testdata/eval_log_vosk.txt`。

**合成集的 100% 是上界，不是现场指标**（现场指标见 7.1），读的时候请注意：

* 语音是 TTS（同一种声学引擎、同一录音链路），真人 + 真实麦克风/房间要重新验收；
* 噪声是粉红噪声 + 合成脉冲响应，不是真实场馆底噪；
* 注册和测试都用了同一批 32 条短语，真实比赛还会出现没注册过的说法（会走"请再说一遍"）。

DTW 模板法做过跨音色对照（用「Yaoyao」音色注册、用「Huihui」音色测试，同样是 100%），
但这只能说明合成音色之间差异不大；**真人换人必须重注册**（`tools/enroll.py --mic`），
这也是本项目改用 Vosk 的原因：不需要注册、换人不用管。

## 8. 唤醒词与口令建议（个人自用场景）

### 8.1 唤醒词

选唤醒词只有一条硬标准：**不能出现在球友的日常对话里**。所以「裁判」不如「小裁判」，
「乒乓球」「开始」「加油」这类高频词直接排除。几个备选（改 `config.json` 的 `wake_words` 即可，
支持写多个唤醒词）：

| 候选 | 音节 | 评价 |
|---|---|---|
| **小裁判**（当前） | xiǎo cái pàn | 语义贴切、3 音节不易误触发，球场上没人会这么说 |
| 小乒乓 | xiǎo pīng pāng | 更贴项目、音色辨识度高；注意"乒乓"本身在球场高频，所以必须带"小" |
| 嗨裁判 / 你好裁判 | hāi cáipàn | 英文"嗨"开头，抗误唤醒最稳，代价是说得稍别扭 |
| 记分员 | jì fēn yuán | 语义直白，老人也懂 |

建议做法：**同时注册 2 个唤醒词**（例如「小裁判」+「小乒乓」），
现场哪个更顺手用哪个；Vosk 的 grammar 会同时支持，代价几乎为零。
如果想更"有人味"，可以让播报也换口气：唤醒时播"在"（已实现），加分时播"左方加一分，三比二"。

### 8.2 口令

已经按"个人自用、说话随便一点"扩充过一轮（都在 `config.json`，49 条说法）：

* 计分：`左方加一分 / 左边加一分 / 左方加分 / 左加一分 / 左面加一分`（右方同理）
* **个人映射**：「我加一分」「给我加一分」「这分算我的」→ 落到你所在的一侧，
  由 `self_side`（默认 `left`）决定；「对方加一分」「给他加一分」「对面加一分」→ 另一侧。
  这样你自己打球时不用记"左/右"，说"我加一分"就行。
* 撤销：「刚才不算」「这分不算」「退回去」……
* 重置：「重来」「重新计分」……（仍然要二次确认，避免误清零）
* 报分：「我几比几」「现在多少分」……（机器人会念比分）
* 结束：「暂停」「先不打了」……

给机器人的建议：

1. **危险动作走二次确认**（重置比分已经是"说两遍"），比"猜一个意图"安全得多；
2. 想加"播报音量/静音"这类指令（"声音大点""别说话"）也容易，加两条 phrase + 一个新 intent 即可；
3. 没听清时固定播"请再说一遍"，不要播"没听懂您说什么"这种长句——长播报会盖住用户的下一次尝试。

**口令卡（推荐照着这张说）**

真人验收的数据很明确：4 字以上的说法 39/39 全对，2 字说法只有 3/8。
短说法仍然有效（安静、近场、链路好时），平时请优先用左边这些：

| 想干什么 | 推荐说法（长） | 短说法（应急） |
|---|---|---|
| 我得分 | 我加一分 / 这分算我的 | — |
| 对方得分 | 对方加一分 / 对面加一分 | — |
| 按左右侧加分 | 左方加一分 / 右方加一分 | 左加一分 / 右加一分 |
| 撤销 | 撤销上一分 / 刚才不算 / 这分不算 | 撤销 |
| 重置 | 重新计分 / 重新开始记分 / 比分清零 | 重来 |
| 确认这一分 | 确认这一分 / 确认得分 | 确认 |
| 报分 | 现在比分 / 我几比几 / 现在多少分 | 报分 |
| 结束 | 先不打了 / 取消操作 / 不用了 | 退出 / 结束 / 暂停 |

### 8.3 只有蓝牙耳机时怎么办（当前实际条件）

蓝牙耳机的通话链路（HFP）是这次掉首字的主要嫌疑，但它仍然能用，按下面顺序榨出最好效果：

1. **先量，再改**：`python tools/check_mic.py --device <编号>`。它会告诉你每条录音的
   起音有没有能量、峰值/RMS、4kHz 以上能量占比、以及当场解码结果。
   **换另一副耳机/换摆位/改完设置后再跑一次**，直接对比那三列数字 —— 这是唯一能判断
   "哪副耳机更好"的客观办法。
2. 明显信号：**4kHz 以上能量占比 < 2%** 说明走的是窄带通话链路（8kHz，CVSD），
   高频被砍掉，而"撤/出/报/错"这些字恰好靠高频区分 —— 这种链路下短口令基本没救，
   优先用长说法（见 8.2 的口令卡）；如果另一副耳机这段占比明显更高，就用那副。
3. **Windows 侧要检查的三处**（声音设置 → 录制 → 该耳机 → 属性）：
   * "高级"里采样率选 **16 kHz**（别用 8 kHz）；
   * "增强/音频增强"里的**噪音抑制、回声消除**先关掉试一次（有些实现会把起音当噪声吃掉），
     再打开试一次，用 `check_mic.py` 对比——不同驱动行为差别很大；
   * 记得把该设备设为"默认通信设备"，避免系统切换到别的端点。
4. **用新录音工具**：`record_dataset.py` / `enroll.py` 已经是"流只开一次 + 起音前 0.5s 缓存 +
   开口前先响提示音"，这三点专门针对蓝牙链路。听到提示音再开口，不要抢。
5. 麦克风杆尽量靠近嘴、别朝外；说话别太快，2 字口令更要放慢。
6. 实在不行还有一条替代路径：**用手机录音 App 导出 WAV（16-bit PCM、单声道）**，
   放进一个目录并照 `realdata/labels.json` 的格式写标签，然后用 `eval` 评——
   这能验证"识别逻辑"是否够用（手机麦克风远好于蓝牙通话麦），只是不能代替实时链路测试。

### 8.4 阵列麦 + 1~2 米距离（正式部署时）

* 阵列麦通常只支持 44.1k/48k：`MicSource` 现在会自动按原生采样率打开，再**流式重采样**到 16k
  （跨块保持相位，不会在块边界抖）。
* 1~2 米是"中远场"，实测我们造的远场样本（混响+8dB SNR）Vosk 仍能唤醒；
  建议麦克风放在机器人朝球台的一侧、**别贴着扬声器**，并把阵列自带的降噪/波束成形打开。
* **机器人自己在说话时要闭嘴听**：播报期间识别会静音（半双工，`app.py` 里对
  `speaker.is_speaking` 的判断），否则喇叭里的"左方1比0"可能把自己唤醒。
  如果阵列支持 AEC（回声消除），开上更好，可以真正全双工。
* 现场噪声调参顺序：先看 `runtime/events.jsonl` 里有没有被噪声骗到的 `wake`，
  再调 `vad_margin_db`（调大更保守）和 `match_threshold`。

## 9. 局限与下一步

1. **必须用真人录音做一次现场验收**：按方案 4.5 的做法录 2–4 小时，
   拆成"唤醒词单说 / 口令单说 / 连说 / 干扰句"四类统计，指标口径与上面保持一致。
2. 唤醒目前是"VAD 切句 + 子序列 DTW"，句内的唤醒词能命中；如果要做**真正的滑窗常驻唤醒**
   （每 100ms 跑一次匹配、不依赖断句），需要把 `dtw_engine._match_segment` 换成固定窗口版本，
   代价是 CPU 上升，RK3588 上仍有余量。
3. 连续加速说话、两个人同时说话、强混响场景仍是弱项；现场可用 `tools/inspect_dtw.py`
   看逐段距离，再决定加注册遍数还是换 Vosk/sherpa-onnx KWS。
4. 上板建议：DTW 链路纯 numpy，可直接在 RK3588 的 CPU 上跑；
   `sounddevice` 换成 `arecord`/ALSA 采集即可，其余代码不用动。
5. 实体按键后备接口已预留：按键直接调 `ScoreBoard.apply("score_left"...)` 即可，
   和语音共用同一套状态机与日志。

## 10. 常见问题

* **`mic` 报 "Invalid device" 或 "Blocking API not supported yet"**：
  采集已改成回调式（阻塞式在 WDM-KS 驱动上会被 PortAudio 拒绝），并且会自动降混双声道。
  如果仍然打不开，先跑 `python -m tt_voice.cli devices` 看设备列表：
  这台开发机上只枚举到 3 个 WDM-KS 输入端点、**没有默认输入设备、也打不开**，
  大概率是 Windows 麦克风权限或 Realtek 驱动 pin 没激活（声音设置里确认麦克风可用后再试）。
  离线链路（`wav` / `text` / `eval`）不依赖麦克风。
* **模型下载慢**：`alphacephei.com` 直连时只有 6–23 KB/s，开代理后实测 0.6–1.3 MB/s（42MB 约 1 分钟）。
  也可以用 `tools/download_model.py --url <镜像>`，或手动把模型目录放到 `models/` 下并保持目录名。
  模型已就位并跑通验收（见第 7 节）。
* **`selftest` 报找不到模板库**：先跑一次 `tools/enroll.py`（没有麦克风可以先用
  `--tts "Microsoft Huihui" --tts-rates -1 1` 造一套，仅用于自测）。
* **改了口令表但口令不生效**：DTW 后端需要重新注册（模板按短语存储）；
  Vosk 后端改完 `config.json` 重启即可，grammar 会自动重建。
* **误识别太多**：先把 `dtw_margin` 调大（1.2 → 1.4），再看 `runtime/events.jsonl`
  里 `raw_text` / `similarity` 定位是"听错"还是"判太松"。
